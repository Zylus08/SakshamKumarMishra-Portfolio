## 2. Article 3 Analysis: Why My Faster Kernels Made PyTorch Training Slower

### 2.1 Research Question & Core Hypothesis
In modern deep learning systems, memory bandwidth frequently bounds training throughput. Fusing element-wise operations (such as residual addition and activation functions) is widely cited in literature as a primary optimization to eliminate redundant DRAM round-trips.

The central research hypothesis was:
> *Hypothesis $H_1$: Replacing PyTorch’s stock separate residual addition and ReLU activation kernels with custom AVX2 SIMD fused forward and backward C++ kernels will increase end-to-end training throughput on x86_64 CPU hardware.*

### 2.2 The Zero-Mask Architecture & AVX2 Kernel Implementation
To maximize memory bandwidth savings, FORGE introduced the **Zero-Mask Architecture**:
- In standard PyTorch autograd, evaluating $y = \text{ReLU}(x + \text{residual})$ saves an intermediate boolean mask tensor in DRAM to indicate which elements were positive during the forward pass.
- In FORGE's zero-mask design, the forward pass saves **only the output activation tensor $y$**.
- During the backward pass, the gradient condition is recomputed directly in AVX2 SIMD registers:
  ```cpp
  // AVX2 SIMD register condition re-evaluation:
  __m256 y_val = _mm256_loadu_ps(&output[i]);
  __m256 grad_val = _mm256_loadu_ps(&grad_output[i]);
  __m256 mask = _mm256_cmp_ps(y_val, _mm256_setzero_ps(), _CMP_GT_OQ);
  __m256 grad_in = _mm256_and_ps(grad_val, mask);
  _mm256_storeu_ps(&grad_input[i], grad_in);
  ```
- This completely eliminated the allocation, writes, and reads of intermediate mask tensors in DRAM.

### 2.3 Numerical Verification Contract
Prior to performance benchmarking, FORGE established strict numerical correctness criteria:
- **Bitwise Parity:** Evaluated against stock PyTorch across **3,674,112 elements** over 29 test configurations.
- **Maximum Absolute Error:** $L_\infty = \max |y_{\text{forge}} - y_{\text{stock}}| = 0.0$ (exact bitwise parity).
- **Regression Pass Rate:** **29 / 29 tests passed** across zero-mask edge cases, boundary conditions ($x = 0$), and multi-threaded partition boundaries.

### 2.4 Empirical Findings: The Certified Slowdown
Performance was evaluated under frozen experimental conditions:
- **Model:** ResNet-20 on CIFAR-10 (batch size 128).
- **Hardware:** Hybrid x86_64 CPU host (Intel Alder Lake Core i7-12650H, 16 GB DDR5).
- **Harness:** Multi-process isolation, 3 warmup epochs, 10 timed epochs.

**Finding:** The custom AVX2 kernels were micro-benchmarked as up to 3× faster in isolation, yet end-to-end training achieved **0.8504× stock throughput** (513.2 vs 603.5 samples/sec, representing **14.96% lower throughput** and **17.59% higher step latency**).

### 2.5 Forensic Analysis via Amdahl's Law
Why did faster SIMD kernels cause end-to-end training to decelerate?

1. **Amdahl's Law Fraction Analysis:**
   - In ResNet-20, 2D convolutions consume **49.43%** of training step time.
   - Batch normalization consumes **33.05%** of training step time.
   - Unaccelerated PyTorch operations total **82.48%** of the step.
   - The fused Add+ReLU operation accounted for only **8.80%** of the baseline runtime.

2. **Theoretical Speedup Ceiling:**
   Applying Amdahl's Law:
   $$S_{\text{theoretical}} = \frac{1}{(1 - f) + \frac{f}{s_{\text{kernel}}}} = \frac{1}{(1 - 0.0880) + \frac{0.0880}{\infty}} = \frac{1}{0.9120} \approx 1.0965\times$$
   Even if the fused kernel executed instantaneously ($s_{\text{kernel}} = \infty$), the absolute maximum possible training speedup was only **9.65%**.

3. **The Overhead Tax:**
   - In invoking custom C++ extension kernels from Python, PyTorch performs dynamic tensor argument parsing, thread state synchronization, and memory layout checks.
   - In channels-last configurations, implicit layout conversions between NCHW and NHWC introduced redundant memory copies that overwhelmed all AVX2 SIMD computational savings.

### 2.6 Scientific Value of Reporting Negative Results
Publishing negative results is essential to preventing cargo-cult optimization:
- Micro-benchmarking an isolated operator can be dangerously misleading when operator execution time is dwarfed by framework dispatch and memory copy overheads.
- Kernel fusion must target the dominant operations (convolutions and matrix multiplications) rather than element-wise tails to deliver end-to-end gains.

## 3. Article 4 Analysis: Where Does the Time Go in CPU Language-Model Inference?

### 3.1 Research Question & Core Challenge
Local execution of large language models on commodity consumer CPUs is critical for privacy and edge autonomy. However, commodity CPUs lack the terabyte-per-second high-bandwidth memory (HBM) of server GPUs.

The investigation centered on:
> *Research Question: Where does execution time actually go during quantized CPU transformer inference, and how close to the microarchitectural hardware roofline can a clean-room C++ engine perform without a heavy runtime framework?*

### 3.2 Microarchitectural Kernel Implementation & Block Quantization
VECTRA implemented clean-room AVX2 SIMD kernels for the Qwen2.5-1.5B-Instruct architecture:
- **Quantization Schemes:**
  - **Q4_K (4.50 bits/weight):** Super-blocks of 256 weights subdivided into eight 32-weight blocks. Each block holds 4-bit nibbles with 6-bit quantized scales and offsets.
  - **Q6_K (6.56 bits/weight):** Super-blocks with 6-bit quantized weights, higher dynamic range for sensitive projection layers.
- **AVX2 INT8 GEMV Microarchitecture:**
  - Unpacks 4-bit weights into 8-bit integer vectors using `_mm256_and_si256` and `_mm256_srli_epi16`.
  - Performs 16-bit intermediate signed multiply-add using `_mm256_maddubs_epi16`.
  - Horizontally reduces into 32-bit accumulators via `_mm256_madd_epi16`.

### 3.3 Arithmetic Intensity & Roofline Model
The research note formalizes the distinct execution regimes of transformer inference:

#### The Memory-Bound Decode Phase
In autoregressive token generation, a single token is generated per step. The model must stream all weight tensors from main memory to CPU caches once per generated token:
- For $P = 1.54 \times 10^9$ parameters quantized to $W = 1.06\text{ GB} = 1.06 \times 10^9\text{ bytes}$:
$$\text{FLOPs} = 2 \times 1.54 \times 10^9 = 3.08 \times 10^9\text{ FLOPs}$$
$$I_{\text{decode}} = \frac{\text{FLOPs}}{\text{Bytes Transferred}} = \frac{3.08 \times 10^9}{1.06 \times 10^9} \approx 2.91\text{ FLOP/byte}$$
On an Intel Core i7-12650H with DDR5 memory exhibiting a measured STREAM Triad practical bandwidth of $B_{\text{mem}} \approx 36.8\text{ GB/s}$ (and analytical channel peak of $38.4\text{ GB/s}$):
$$\text{Machine Balance} = \frac{\text{Peak Compute (GFLOP/s)}}{\text{Peak Bandwidth (GB/s)}} = \frac{450}{36.8} \approx 12.23\text{ FLOP/byte} \quad \left(\text{or } \frac{450}{38.4} \approx 11.72\text{ FLOP/byte}\right)$$
Because $I_{\text{decode}} = 2.91 < 11.72$, execution is deeply memory-bandwidth bound. The theoretical single-thread decode throughput ceiling is:
$$\text{Throughput}_{\text{STREAM}} = \frac{36.8\text{ GB/s}}{1.0656\text{ GB}} \approx 34.5\text{ tokens/second} \quad \left(\text{or } \frac{38.4\text{ GB/s}}{1.06\text{ GB}} \approx 36.2\text{ tok/s theoretical channel ceiling}\right)$$

#### The Compute-Bound Prefill Phase
During prompt processing, all $T$ prompt tokens are evaluated concurrently:
$$I_{\text{prefill}} = \frac{2 \cdot T \cdot P}{P_{\text{bytes}}} = T \cdot I_{\text{decode}}$$
For prompt length $T = 512$, arithmetic intensity reaches $I_{\text{prefill}} \approx 1,600\text{ FLOPs/byte}$, transitioning the kernel from memory-bandwidth-bound into compute-bound vector execution.

### 3.4 Multi-Projection SIMD Fusion & Thread Barrier Elimination
Standard inference runtimes execute separate matrix-vector multiplications for Query ($W_Q$), Key ($W_K$), and Value ($W_V$) projections, introducing thread pool barriers and cache thrashing between passes.

VECTRA introduced **Multi-Projection SIMD Fusion**:
- Combines $W_Q$, $W_K$, and $W_V$ weights into a single contiguous linear projection pass.
- Thread workers evaluate query, key, and value vectors in a single pass through cache without synchronization barriers between projection steps.

### 3.5 The Zero-Graph Pre-Allocated Memory Architecture
Rather than constructing dynamic computational graphs that allocate and free intermediate activation buffers per token:
- VECTRA pre-allocates an immutable execution arena during model loading.
- Working memory is strictly capped at **1,061.4 MB**, maintaining a strict $\le 1.10\text{ GB}$ ceiling and saving **111 MB** compared to `llama.cpp` on identical workloads.
