## 2. Article 1 Analysis: What Happens When a SQL Query Outgrows Memory?

### 2.1 Editorial Thesis & Problem Statement
Most database tutorials demonstrate query engines executing on in-memory collections of a few thousand records. Under such conditions, naive nested loop joins and standard in-memory hash tables appear fast. However, when the volume of intermediate records exceeds physical memory, the engine must transition from pure CPU calculation to external memory management. Failure to design bounded disk-spilling protocols into operator interfaces from day one leads to unbounded heap allocations, OS swap thrashing, out-of-memory kernel panics, and massive performance degradation.

### 2.2 Structural Section Breakdown

#### Section 1: The Query That Broke the Buffer
- Introduces a concrete analytical query joining a 20-million-row `orders` table with an 80-million-row `order_items` table, aggregating sales volume across dates.
- Calculates memory requirements: an in-memory hash table for 20 million orders requires $\approx 3.2\text{ GB}$ of RAM. Under an execution quota of `--max-memory=256MB`, naive execution fails catastrophically.

#### Section 2: From Text to Physical Operators: Setting the Execution Context
- Succinctly establishes the lifecycle of the query from SQL text through lexing, recursive descent parsing, catalog name binding, logical plan optimization, and physical operator lowering.
- Focuses on the physical operator tree: `PhysicalSort` $\to$ `PhysicalAggregate` $\to$ `PhysicalHashJoin` $\to$ `PhysicalScan`.

#### Section 3: Formalizing the External Memory Problem
- Establishes mathematical definitions:
  - Input relations $R$ (build side) and $S$ (probe side).
  - Page block size $B$ (AXIOM uses 64 KB blocks).
  - Memory budget $M$ measured in blocks: $B_{\text{mem}} = \lfloor M / B \rfloor$.
  - Proves that when $|R| > B_{\text{mem}}$, naive in-memory hash join triggers $O(|R| \cdot |S|)$ nested disk scans unless partitioned.

#### Section 4: Grace Hash Join: Divide, Partition, and Conquer
- Details the two-phase Grace partitioning algorithm:
  - **Phase 1 (Partitioning):** Stream relation $R$, apply hash function $h_1(k) \pmod K$ to assign tuples to $K$ output partitions on disk. Stream relation $S$, partition with the identical hash function $h_1$.
  - **Phase 2 (Build & Probe):** For each partition $i \in [0, K-1]$, load build partition $R_i$ into an in-memory hash table using secondary hash function $h_2 \neq h_1$. Stream probe partition $S_i$ through the table, emitting matches.
- Derives the bounded I/O complexity:
  $$\text{I/O}_{\text{Grace}} = 2 \cdot \left( \frac{|R| + |S|}{B} \right) + \frac{|R| + |S|}{B} = 3 \cdot \left( \frac{|R| + |S|}{B} \right)$$

#### Section 5: Bounded Build Blocks and Skew Handling in Practice
- Analyzes key skew failure modes: when 40% of records share identical join keys, partition $R_{\text{skew}}$ exceeds $M$ even after partitioning.
- Details AXIOM's recursive sub-partitioning protocol using salt modifiers: $h_{1, d}(k) = \text{xxHash64}(k, \text{seed}_d) \pmod K$.
- Explains hybrid hash join fallbacks when partitions contain identical duplicate keys.

#### Section 6: Hierarchical External Merge Sort and Bounded Fan-In
- Details the implementation of `PhysicalSort` under memory limits:
  1. **Run Generation:** Accumulate batches up to memory budget $M$, sort in-memory via `std::sort`, flush to sorted binary run files (`run_0.axmb`, `run_1.axmb`).
  2. **Bounded Fan-In K-Way Merge:** Merge $F$ runs concurrently using a min-heap priority queue (`std::priority_queue`).
  3. **File Descriptor & Buffer Management:** Demonstrates why fan-in must be strictly bounded ($F \le 32$) to prevent OS file descriptor exhaustion (`EMFILE`) and per-stream buffer fragmentation.

#### Section 7: Partitioned External Aggregation
- Describes two-pass hash aggregation: streaming input tuples into an aggregate hash table; when memory reaches threshold, spilling frozen intermediate aggregate states to disk, followed by a secondary reduction pass.

#### Section 8: AXMB v1: Designing a Temporary Spill Container
- Introduces AXIOM's custom binary container format (`AXMB v1`), eliminating CSV/JSON text serialization overhead:
  - Fixed 64-byte block header with magic bytes `'AXMB'`.
  - Bit-packed null bitmap (1 bit per column value).
  - Variable-length string offset table.
  - Contiguous fixed-width primitive data payload.
  - Per-block xxHash-64 checksum for data corruption detection on SSDs.
  - RAII resource handles ensuring temporary `.axmb` files are automatically unlinked on normal completion or error unwinding.

#### Section 9: The Memory Accounting Gap: Tracked Buffers vs. Process RSS
- Discusses the subtle difference between engine-tracked memory buffers and OS Resident Set Size (RSS):
  - Memory allocators (`glibc ptmalloc`, `tcmalloc`) retain freed memory in thread caches rather than immediately returning pages to the kernel via `brk`/`madvise(MADV_DONTNEED)`.
  - Explains how AXIOM enforces strict page-aligned buffer pools to ensure that memory limits correspond to physical memory reality.

#### Section 10: Empirical Verification & Lessons Learned
- Summarizes empirical benchmarks:
  - Successfully joined **5.37 GB** out-of-core dataset on a **256 MB** buffer allocation.
  - Achieved **120 / 120 passed (100% parity)** on differential correctness tests compared byte-for-byte against DuckDB 2.0.0.

## 3. Article 2 Analysis: Building a C++ Interpreter Changed How I Think About Memory

### 3.1 Editorial Thesis & Problem Statement
Writing an interpreter from scratch in modern C++ is one of the most effective ways to demystify programming language semantics. While novice developers view variables as simple name-value pairs, an interpreter author must implement the concrete mechanics of scope resolution, activation frames, reference lifetimes, and circular references. This essay documents the transition from a naive pointer-based object model to an industrial handle-based memory architecture.

### 3.2 Structural Section Breakdown

#### Section 1: The Illusion of Variables
- Analyzes the abstract mental model of programmers: variables as named boxes holding values.
- Deconstructs what a variable actually is at the machine and runtime level: an offset in a call frame, a key in an environment symbol table, or an address in heap storage.

#### Section 2: The Naive Trap: Pointer-Chasing AST Nodes
- Reviews the standard beginner approach: creating raw C++ pointer links (`ASTNode*`, `std::shared_ptr<Object>`) between syntax tree nodes and runtime values.
- Identifies failure modes:
  - Dangling pointers when child scopes exit before closures.
  - Unbounded reference count cycles causing silent memory leaks.
  - Cache thrashing caused by scattered heap allocations.

#### Section 3: The Abstract Validated Handle Reference Model
- Introduces PRAXIS's core architectural abstraction: the *Abstract Validated Handle Reference Model*.
- Replaces raw memory pointers with compact 32-bit generational handles (`Handle<T>`):
  - 20 bits: dense index into a centralized object arena.
  - 12 bits: generation counter incremented on every slot reuse.
- Explains the benefits:
  - Dereferencing an invalid or stale handle produces an immediate runtime diagnostic rather than memory corruption or undefined behavior.
  - Object compaction and relocation can occur without invalidating external references.

#### Section 4: Environment Frames and Dynamic Scoping Chains
- Details how lexical scope is implemented in PRAXIS:
  - An `Environment` represents an activation frame stored as a vector of handle bindings.
  - Each frame holds a handle to its enclosing parent frame (`parent_handle`).
  - Resolving a variable name traverses the lexical frame chain:
    $$E_0 \leftarrow E_1 \leftarrow E_2 \leftarrow \dots \leftarrow E_{\text{global}}$$
  - Explains how closures capture their lexical parent frame handle, keeping the environment chain alive even after outer functions return.

#### Section 5: Value Semantics vs. Reference Semantics
- Explores how PRAXIS partitions data types into distinct memory models:
  - **Value Types (Scalars):** 64-bit integers, IEEE-754 doubles, booleans, and short strings stored directly inside an 8-byte tagged union (`Value`). Copied by bitwise assignment.
  - **Reference Types (Heap Objects):** Arrays, dictionaries, user-defined class instances, and closures allocated in the handle arena. Variables store handles; copies duplicate the handle without cloning heap payloads.

#### Section 6: The RAII Bridge: Native C++ Managing Runtime Lifetimes
- Details how native C++ RAII resource management governs interpreter runtime resources:
  - Scoped interpreter frames wrapped in C++ destructors.
  - Temporary expression evaluation stacks automatically unroll and clear handles during C++ exception unwinding (e.g., when a runtime error or syntax exception is thrown).

#### Section 7: The Dark Corner: Circular References and Self-Referential Closures
- Analyzes the classic circular reference problem:
  - An object `A` holds a handle to object `B`, which holds a handle back to `A`.
  - A closure capturing its own function name within its lexical environment.
- Details PRAXIS's solution: combining generational handle tracking with scoped frame destruction to break cycles upon environment disposal without requiring a heavyweight stop-the-world garbage collector.

#### Section 8: Lessons from 258 MSVC Differential Verifications
- Documents empirical validation of the PRAXIS interpreter:
  - **258 / 258 differential programs passed** (137 M1 + 79 M2 + 42 M3) compiled with native MSVC (`cl.exe /std:c++20 /EHsc /Od /Zc:nrvo-`) and compared byte-for-byte against Praxis execution with a 100.0% pass rate.
  - An additional **13 adversarial safety programs** verified that invalid operations (use-after-free, double deletion, deleting stack variables) were cleanly trapped without crashing the host interpreter.

#### Section 9: Engineering Conclusions
- Concludes with overarching systems takeaways:
  1. Handle indirection provides memory safety and diagnostic clarity that raw pointers cannot match.
  2. RAII in C++ is sufficient to build robust, leak-free runtime interpreters when paired with generational arena storage.
