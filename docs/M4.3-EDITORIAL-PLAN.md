## 3. Detailed Editorial Plans for the Four Articles

### Article 1 (Engineering Essay): AXIOM
- **Title:** *What Happens When a SQL Query Outgrows Memory?*
- **Route:** `/writing/sql-query-outgrows-memory`
- **Category:** `Engineering` | **Word Count:** ~2,250 words
- **Audience:** Database architects, distributed systems engineers, high-performance computing specialists.
- **Narrative Arc:**
  1. *The Query That Broke the Buffer:* Concrete analytical query joining orders and order_items with aggregations.
  2. *From Text to Physical Operators:* Fast-forward through lexer, AST, catalog binding, and physical tree generation.
  3. *Formalizing the External Memory Problem:* Mathematical proof of $O(|R| \cdot |S|)$ memory blowup.
  4. *Grace Hash Join (Divide, Partition, and Conquer):* Phase 1 partitioning, Phase 2 build and probe, mathematical I/O bound:
     $$\text{I/O}_{\text{Grace}} = 3 \cdot \left( \frac{|R| + |S|}{B} \right)$$
  5. *Bounded Build Blocks & Skew Handling:* Handling non-uniform key distributions via sub-partitioning and fallback.
  6. *Hierarchical External Merge Sort:* Run generation via `std::sort`, priority-queue k-way merge with bounded fan-in $F$.
  7. *Partitioned External Aggregation:* Two-pass hash aggregation and intermediate spill batches.
  8. *AXMB v1 Temporary Spill Container:* Proprietary binary batch layout, bit-packed nulls, xxHash-64 block verification, RAII eviction.
  9. *The Memory Accounting Gap:* Engine tracked buffers vs. C++ allocator heap fragmentation and OS RSS.
  10. *Empirical Validation & Key Takeaways:* 5.37 GB join on 256 MB buffer, 120/120 DuckDB differential test parity.

- **Route:** `/writing/building-a-cpp-interpreter`
- **Category:** `Engineering` | **Word Count:** ~2,250 words
- **Audience:** Compiler engineers, runtime developers, systems programmers transitioning between managed and native languages.
- **Narrative Arc:**
  1. *The Illusion of Variables:* Confronting how programmers take names and scopes for granted.
  2. *The Naive Trap: Pointer-Chasing AST Nodes:* Exploring why direct object graphs lead to dangling references and memory corruption.
  3. *The Abstract Validated Handle Reference Model:* Indirection through 32-bit generation-indexed handles (`Handle<T>`).
  4. *Environment Frames and Dynamic Scoping Chains:* Lexical scoping as persistent frame vectors with parent link pointers.
  5. *Value Semantics vs. Reference Semantics:* Primitive scalar types vs. structured heap objects and mutable handles.
  6. *The RAII Bridge: Native C++ Managing Runtime Lifetimes:* Wrapping runtime objects in C++ RAII resource handles.
  7. *The Dark Corner: Circular References and Self-Referential Closures:* How cycle detection and frame deallocation prevent leaks.
  8. *Lessons from 258 MSVC Differential Verifications:* 258 distinct programs (137 M1, 79 M2, 42 M3) verified byte-for-byte against native MSVC (`cl.exe`), plus 13 adversarial safety checks.
  9. *Engineering Conclusions:* How building an interpreter deepens mental models of modern C++ resource management.

### Article 3 (Research Note): FORGE
- **Title:** *Why My Faster Kernels Made PyTorch Training Slower*
- **Route:** `/research/faster-kernels-slower-training`
- **Category:** `Efficient ML` | **Status:** `Independent exploration` | **Word Count:** ~2,650 words
- **Audience:** ML systems researchers, PyTorch compiler engineers, kernel optimization specialists.
- **Narrative Arc:**
  1. *Introduction & Research Question:* Can fusing residual additions with ReLU activations in native AVX2 SIMD yield end-to-end training speedups?
  2. *Experimental Setup & Frozen Workload:* ResNet-20 on CIFAR-10, batch size 128, Alder Lake host hardware.
  3. *The Zero-Mask Architecture & AVX2 Kernel Design:* Fusing forward and backward passes, eliminating intermediate boolean masks via vector register condition re-evaluation.
  4. *Numerical Verification & IEEE-754 Contract:* Bitwise $L_\infty = 0.0$ parity across 3,674,112 elements (29/29 regression tests passing).
  5. *Benchmarking Methodology:* Subprocess isolation, warmup epochs, median wall-clock iteration timing.
  6. *Empirical Results:* Stock PyTorch: 212.11 ms/step (603.5 samples/s) vs. FORGE fused: 249.43 ms/step (513.2 samples/s) → **0.8504× stock throughput (513.2 vs 603.5 samples/sec, 14.96% lower throughput, 17.59% higher step latency)**.
  7. *Forensic Analysis (Amdahl's Law Bottleneck):*
     - Fused operations represent only 8.80% of total training step time.
     - PyTorch convolution (49.43%) and batch normalization (33.05%) consume 82.48%.
     - Theoretical Amdahl ceiling was only $S_{\text{max}} = 1.0965\times$.
     - PyTorch C++ extension dispatch overhead and tensor layout memory copies consumed all SIMD savings.
  8. *Threats to Validity & Unperformed Experiments:* CPU-only constraints, batch size limitations, single-host Alder Lake boundary.
  9. *Hypothesis Revision & Scientific Conclusions:* Why negative results are essential engineering milestones.

### Article 4 (Research Note): VECTRA
- **Title:** *Where Does the Time Go in CPU Language-Model Inference?*
- **Route:** `/research/cpu-language-model-inference`
- **Category:** `Efficient ML` | **Status:** `Independent exploration` | **Word Count:** ~2,650 words
- **Audience:** LLM runtime developers, edge AI engineers, computer architects.
- **Narrative Arc:**
  1. *Introduction & Architectural Problem:* The memory-bandwidth bottleneck of edge CPU transformer inference.
  2. *Workload Definition & Frozen Model Identity:* Qwen2.5-1.5B-Instruct frozen weights, GGUF format, 5 prompt + 32 generation tokens.
  3. *End-to-End Inference Data-Flow Architecture:* Token embedding, RMSNorm, Multi-Head Attention, RoPE, SwiGLU MLP, LM-head projection.
  4. *Block Quantization Representations:* Mathematical structures of Q4_K (4.50 bpw) and Q6_K (6.56 bpw).
  5. *Microarchitectural Kernel Implementation:* AVX2 INT8 GEMV, `_mm256_maddubs_epi16`, `_mm256_madd_epi16` dot product vectorization.
  6. *Arithmetic Intensity & Roofline Analysis:*
     $$I_{\text{decode}} = \frac{2 \cdot P}{P_{\text{bytes}}} = \frac{2 \cdot 0.5 \cdot 10^9}{0.3125 \cdot 10^9} = 3.20\text{ FLOPs/byte}$$
     Comparing decode (memory bandwidth bound) vs. prefill (compute bound).
  7. *Multi-Projection SIMD Fusion & Thread Barrier Elimination:* Fusing QKV projections into a contiguous GEMV call, eliminating synchronization barriers.
  8. *The Zero-Graph Pre-Allocated Memory Architecture:* Pre-allocating working memory to strictly enforce a $\le 1.10\text{ GB}$ resident memory footprint (1,061.4 MB actual, saving 111 MB vs. llama.cpp).
  9. *Empirical Results & Benchmark Ledger:* Sustained median decode throughput of **16.82 tok/s** (19.97 tok/s peak).
  10. *Prefill vs. Decode Dynamics:* Comparing arithmetic intensity, compute rooflines, and multi-threaded scaling.
  11. *Threats to Validity & Generalization Boundaries:* Qwen2.5 model boundary, absence of register-tiled GEMM for long prefill.
  12. *Conclusions & Future Research:* Quantized KV cache and core affinity pinning.
