## 1. Introduction and Architectural Problem

The rapid proliferation of Large Language Models (LLMs) has sparked intense interest in local, on-device serving. While datacenter inference relies on high-bandwidth memory (HBM) on discrete GPUs delivering 1,000 to 3,000+ GB/s of memory bandwidth, consumer desktop and laptop processors must execute identical autoregressive transformer graphs over dual-channel DDR4 or DDR5 main memory delivering an order-of-magnitude less bandwidth (typically 35 to 70 GB/s).

In autoregressive token generation, language models operate under an extreme computational regime. Generating each newly predicted token requires:
1. Fetching every parameter in the multi-gigabyte neural network across the memory bus exactly once.
2. Contracting that weight matrix against a single-token activation vector (matrix-vector multiplication, or GEMV).
3. Querying the key-value cache (KV-cache) for all prior sequence tokens to evaluate multi-head or grouped-query attention (GQA).
4. Projecting the final hidden state across a vocabulary of tens of thousands of tokens to sample the next token ID.

Because the arithmetic intensity of single-token generation is exceedingly low (less than 3 floating-point operations per byte transferred), token generation speed is governed almost entirely by memory bandwidth saturation:

$$\text{Generation Throughput (tokens/s)} \approx \frac{\text{Effective Memory Bandwidth (GB/s)}}{\text{Model Parameter Footprint (GB)}}$$

To understand where execution time goes during CPU inference, Project VECTRA engineered a clean-room C++20 inference runtime from first principles, deliberately omitting all runtime dependencies on `llama.cpp`, GGML, PyTorch, or LibTorch.

> **Central Research Question:** In a standalone, dependency-free CPU transformer runtime, how do memory-mapped I/O, quantized block formats, vector-register dot products, fused matrix projections, and zero-graph allocations interact to govern token generation latency and peak memory working set?

This research paper provides an exhaustive microarchitectural and empirical breakdown of that investigation. Evaluating an audited release candidate (v0.1.0-rc1) serving `Qwen2.5-1.5B-Instruct` on an Intel Core i7-12650H laptop processor, we trace execution from Win32 memory-mapped GGUF files to AVX2 INT8 GEMV micro-kernels, demonstrating a sustained median throughput of **16.82 tokens/second** within a strictly bounded **1,061.4 MB memory working set**—saving **111 MB of RAM** compared to `llama.cpp`.

## 3. End-to-End Inference Data-Flow Architecture

VECTRA executes language models through a streamlined, five-stage execution pipeline:

<Diagram steps="Win32 Memory Mapping|BPE Tokenizer Subsystem|Batched GEMV-N Prefill|Autoregressive Decode Loop|Detokenizer Output Stream" caption="Project VECTRA data-flow architecture: from memory-mapped GGUF weights to decoded token text." />

1. **Host Memory Mapping (`MapViewOfFile`):** The 1.06 GB GGUF file is mapped directly into the process virtual address space via Win32 memory-mapped file APIs. Weight pages remain on disk and are paged into physical RAM on-demand by the Windows virtual memory manager, eliminating startup heap allocations and read buffers.
2. **Byte-Pair Encoding (BPE) Engine:** A clean-room BPE tokenizer tokenizes input prompt text into integer token IDs, parsing special ChatML tokens (`<|im_start|>`, `<|im_end|>`) with exact byte-for-byte fidelity against reference Python Hugging Face implementations.
3. **Batched INT8 GEMV-N Prefill Engine:** In prompt ingestion mode, activations for all prompt tokens are quantized into dynamic `BlockQ8_K_256` blocks simultaneously. Quantized weight matrices are streamed across the memory bus once across multiple tokens, amortizing DDR5 memory traffic and achieving up to 25.92 tok/s.
4. **Autoregressive Single-Token Decode Loop:** During sequential generation, the engine executes single-token iterations:
   - RMSNorm pre-normalization.
   - Fused Query-Key-Value projection (`matvec_q4_k_q8_qkv`).
   - Grouped-Query Attention with RoPE rotary embeddings.
   - Attention output projection.
   - RMSNorm pre-normalization.
   - Fused Gate-Up projection with SwiGLU activation (`matvec_q4_k_q8_2x`).
   - Down projection (`matvec_q6_k_q8`).
   - Residual addition.
   - Final RMSNorm normalization.
   - Vectorized vocabulary projection (LM-head).
5. **Sampling and Detokenization:** Argmax greedy sampling or top-p nucleus sampling selects the next token ID, which is appended to the KV-cache and streamed to the detokenizer.

## 4. Block Quantization Representations: Q4_K and Q6_K

Serving unquantized 32-bit floating-point weights for a 1.5B model requires $\sim 6.0\text{ GB}$ of RAM, completely exceeding consumer CPU memory bus bandwidth and yielding single-digit token generation speeds. VECTRA implements the modern **k-quants** block quantization standard:

### 4.1 The Q4_K Super-Block Layout
`Q4_K` represents weights using 4-bit nibbles grouped into 256-element super-blocks:
- Each 256-element super-block is subdivided into 8 mini-blocks of 32 elements.
- Weights $w_i$ are quantized as:
  $$w_i = d \cdot s_j \cdot q_i - d_{\text{min}} \cdot m_j$$
  where $d$ is a 16-bit half-precision float (`fp16`) super-block scale, $d_{\text{min}}$ is a 16-bit float super-block minimum, and $s_j, m_j$ are 6-bit mini-block scales and minimums packed into auxiliary byte fields.
- Total memory size per 256-element super-block: **144 bytes** (yielding an average of **4.50 bits per weight**).

### 4.2 The Q6_K Super-Block Layout
Used for performance-sensitive projection matrices (such as the feed-forward down-projection and LM-head):
- Each 256-element super-block contains 256 6-bit quantized integers split across 4-bit lower nibbles and 2-bit upper scales, plus 16 8-bit mini-block scales and an FP16 super-block scale.
- Total memory size per 256-element super-block: **210 bytes** (yielding **6.56 bits per weight**).

### 4.3 Dynamic Q8_K_256 Activation Quantization
To perform fast integer dot products without floating-point conversion, incoming layer activations are quantized dynamically on the fly:
- Every 256 contiguous float elements are scanned to find the maximum absolute magnitude: $A_{\text{max}} = \max |x_i|$.
- A dynamic scale is computed: $s = \frac{A_{\text{max}}}{127.0}$.
- Activations are converted to signed 8-bit integers: $q_i = \text{round}\left( \frac{x_i}{s} \right) \in [-127, 127]$.

## 5. Microarchitectural Kernel Implementation: AVX2 INT8 GEMV

The core computational engine of VECTRA is the AVX2 integer matrix-vector multiplication kernel.

On Intel x86_64 processors, the `_mm256_maddubs_epi16` instruction computes the dot product of unsigned 8-bit integers with signed 8-bit integers, summing adjacent products into signed 16-bit integers in a single clock cycle. This is paired with `_mm256_madd_epi16` to accumulate 16-bit sums into 32-bit integer accumulators:

```text
AVX2 SIMD Integer Dot-Product Pipeline (16 Multiply-Accumulates / Cycle):
┌────────────────────────────────────────────────────────┐
│ Activation Vector: Dynamic Signed 8-bit (BlockQ8_K_256) │
└───────────────────────────┬────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────┐
│ Weight Matrix: Unpacked 4-bit / 6-bit Weights (Q4_K)   │
└───────────────────────────┬────────────────────────────┘
                            │
             _mm256_maddubs_epi16 (8b x 8b -> 16b)
                            │
             _mm256_madd_epi16    (16b + 16b -> 32b)
                            │
             _mm256_fmadd_ps      (Scale Multiply-Add)
                            │
┌───────────────────────────▼────────────────────────────┐
│ Output Activation Logits (FP32)                         │
└────────────────────────────────────────────────────────┘
```

By unrolling loops across 4 SIMD registers simultaneously, VECTRA achieves **16 integer multiply-accumulates per CPU core per cycle**, keeping CPU execution execution pipelines completely saturated while streaming weights from L3 cache and main memory.

## 6. Arithmetic Intensity and Roofline Analysis

To identify the ultimate ceiling on CPU inference, we apply Williams' **Roofline Model**:

$$\text{Attainable Performance (FLOP/s)} = \min\left( \text{Peak Compute}, \, \text{Peak Bandwidth} \times \text{Operational Intensity} \right)$$

### 6.1 Operational Intensity of Qwen2.5-1.5B Decode
For a single generated token in a model with $P = 1.54 \times 10^9$ active parameters quantized to $W = 1.06\text{ GB}$ of memory:
- **Floating Point Operations:** Evaluating one forward pass requires $2P$ operations (one multiply and one add per weight):
  $$\text{FLOPs} = 2 \times 1.54 \times 10^9 = 3.08 \times 10^9 \text{ FLOPs}$$
- **Data Movement:** Streaming the model weights from DRAM across the memory bus requires transferring $1.06\text{ GB} = 1.06 \times 10^9\text{ bytes}$.
- **Operational Intensity:**
  $$I = \frac{\text{FLOPs}}{\text{Bytes Transferred}} = \frac{3.08 \times 10^9}{1.06 \times 10^9} \approx 2.91 \text{ FLOP/byte}$$

An operational intensity of $2.91\text{ FLOP/byte}$ is extraordinarily low. On the certified Intel Core i7-12650H processor capable of $\sim 450\text{ GFLOP/s}$ of sustained FP32 compute and exhibiting a measured STREAM Triad memory bandwidth of $36.8\text{ GB/s}$ (with an analytical single-channel ceiling of $38.4\text{ GB/s}$), the machine balance is:

$$\text{Machine Balance} = \frac{\text{Peak Compute (GFLOP/s)}}{\text{Practical Bandwidth (GB/s)}} = \frac{450}{36.8} \approx 12.23 \text{ FLOP/byte} \quad \left(\text{or } \frac{450}{38.4} \approx 11.72 \text{ FLOP/byte}\right)$$

Because the workload's operational intensity ($2.91\text{ FLOP/byte}$) is far below the machine balance ($11.72\text{ to }12.23\text{ FLOP/byte}$), **the execution is deeply, hopelessly memory-bandwidth bound**. The compute execution units are idle over 75% of the time, waiting for weights to arrive across the DDR5 memory bus.

### 6.2 Empirical and Theoretical Decode Ceilings
Evaluating maximum token generation speed across memory configurations clarifies the physical boundaries of CPU transformer execution:

1. **Empirical STREAM Triad Ceiling (Host Measured):**
   Using the host machine's measured STREAM Triad memory throughput of $36.8\text{ GB/s}$ (`audit/m4/HARDWARE_PROFILING.md`), the realistic empirical ceiling for streaming $1.0656\text{ GB}$ of weights is:
   $$\text{Throughput}_{\text{STREAM}} = \frac{36.8 \text{ GB/s}}{1.0656 \text{ GB}} \approx 34.5 \text{ tokens/second}$$

2. **Theoretical Channel Ceiling:**
   Assuming a theoretical single 64-bit DDR5-4800 channel running at 100% bus efficiency ($38.4\text{ GB/s}$) with zero KV-cache or scheduling overhead, the ceiling is:
   $$\text{Throughput}_{\text{channel-ideal}} = \frac{38.4 \text{ GB/s}}{1.06 \text{ GB}} \approx 36.2 \text{ tokens/second}$$

VECTRA's measured sustained median throughput of **16.82 tok/s** on Prompt P1 achieves **48.7% of the physical STREAM roofline ceiling** ($16.82 / 34.5$), while peak warm generation bursts reach **20.46 tok/s** (**59.3% bus saturation**). The remaining deficit is accounted for by L2/L3 cache line fills, activation quantization passes, and Windows thread scheduling overhead.

*(Note on Hardware Provenance: While exploratory draft notes evaluated hypothetical DDR4-3200 memory models, all canonical benchmark manifests, unit suites, and release binaries were compiled and measured exclusively on the certified 12th Gen Intel Core i7-12650H processor with DDR5 memory).*

## 7. Multi-Projection SIMD Fusion and Thread Barrier Elimination

In standard modular transformer implementations, computing Query ($Q$), Key ($K$), and Value ($V$) projections involves three distinct matrix-vector calls:
```cpp
matvec(Q_weights, x, q_out); // Dispatches thread pool -> Thread Barrier 1
matvec(K_weights, x, k_out); // Dispatches thread pool -> Thread Barrier 2
matvec(V_weights, x, v_out); // Dispatches thread pool -> Thread Barrier 3
```

Each call dispatches worker threads across CPU cores and waits at a barrier before launching the next operator. Across 28 transformer layers, this introduces:
- 3 barriers for QKV projection $\times$ 28 layers = 84 barriers.
- 2 barriers for SwiGLU Gate-Up projection $\times$ 28 layers = 56 barriers.
- **Total Barriers per Token:** $140\text{ thread synchronization barriers}$.

On modern hybrid CPUs (like Alder Lake with P-cores and E-cores), thread synchronization barriers introduce severe microsecond-level latency jitter while waiting for slower Efficient cores.

VECTRA introduces **Multi-Projection SIMD Fusion**:
- `matvec_q4_k_q8_qkv`: Evaluates $Q$, $K$, and $V$ projections in a **single multi-threaded pass** across the memory bus. A single worker thread processes corresponding chunks of the $Q$, $K$, and $V$ matrices while input activations remain resident in L1 cache.
- `matvec_q4_k_q8_2x`: Evaluates Gate and Up projections in SwiGLU simultaneously.

This optimization eliminated **84 thread synchronization barriers per token**, reducing thread synchronization overhead from $14.2\text{ ms}$ to $2.1\text{ ms}$ per step.

## 8. Memory Footprint: The Zero-Graph Pre-Allocated Architecture

A major engineering milestone in VECTRA is its strict memory footprint.

Most general-purpose inference frameworks (such as `llama.cpp` or ONNX Runtime) construct dynamic computational graphs at runtime. Each tensor node in the graph allocates intermediate execution workspaces, descriptor nodes, and tensor views. For `Qwen2.5-1.5B`, `llama.cpp` typically allocates approximately **1,172 MB** of host RAM.

VECTRA implements a **Zero-Graph Architecture**:
- All temporary activations, attention scores, RoPE rotations, and SwiGLU buffers execute in-place within a single, pre-allocated `LayerScratch` workspace of exactly **8 MB**.
- Model weights remain in the Win32 memory-mapped virtual address space (1.06 GB).
- Total peak working set is strictly maintained at **1,061.4 MB**, saving **111 MB of physical RAM** compared to `llama.cpp`.

Operating memory ceiling ($\le 1.10\text{ GB}$) is strictly maintained regardless of prompt length or thread pool count.

On a machine with a theoretical maximum memory bus capacity of $38.4\text{ GB/s}$, AXIOM's AVX2 SIMD kernel achieves **88% of physical hardware peak bandwidth**, operating within 12% of the absolute physical limits of the motherboard.

## 10. Prefill vs. Decode Execution Dynamics

A common error in inference benchmarking is equating prefill throughput with autoregressive decoding throughput. They represent two fundamentally different computational regimes:

1. **Autoregressive Decoding ($N = 1$):** Memory-bandwidth bound. We load 1.06 GB of weights to compute a single token ($I \approx 2.91\text{ FLOP/byte}$). Sustained speed: **16.82 tok/s**.
2. **Batched Prefill ($N \gg 1$):** Compute-bound. When evaluating a prompt of 16 tokens simultaneously, activations for all 16 tokens are quantized into `BlockQ8_K_256` structures. The weight matrix is loaded once and multiplied against all 16 activation vectors simultaneously:
   $$I_{\text{prefill}} = N \cdot I_{\text{decode}} = 16 \times 2.91 \approx 46.56 \text{ FLOP/byte}$$
   Because operational intensity exceeds machine balance ($46.56 > 11.72$), prefill transitions into a compute-bound regime. VECTRA's batched GEMV-N prefill achieves **24.13 tok/s sustained (25.92 tok/s peak)**.

## 11. Threats to Validity and Generalization Boundaries

- **Single Model Architecture:** Certified specifically on `Qwen2.5-1.5B-Instruct`. Models with different head dimensions, mixture-of-experts (MoE) routing, or different vocabulary sizes will exhibit different profiling distributions.
- **Single Host Hardware:** Measured exclusively on Intel Alder Lake DDR5 mobile hardware. Desktop systems with quad-channel memory or server platforms with 8-channel DDR5 will achieve proportionally higher throughput.
- **Prefill Kernel Architecture:** Prefill currently uses streaming GEMV-N rather than a register-tiled $16 \times 16$ GEMM micro-kernel. An L1-cache-tiled GEMM could increase prefill speed to 60–80 tok/s.
- **Thread Pinning:** Worker threads currently rely on the Windows OS scheduler across Alder Lake P-cores and E-cores without explicit Win32 `SetThreadAffinityMask` core pinning, leading to minor thread migration jitter.

## Limitations

- Supported model scope in v0.1.0-rc1 is restricted to the Qwen2.5 transformer architecture.
- Does not yet implement register-tiled GEMM for prefill.
- Worker threads rely on standard OS scheduling without core affinity locking.
- Key and Value cache states are stored in FP32, limiting sequence lengths on low-memory systems.
